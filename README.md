# AGM Research Laboratory (v0.1)

A reproducible research and evaluation laboratory for testing the hypothesis of an
Artificial General Machine (AGM): is *architectural self-determination* measurably
different from fixed agents, adaptive agents, architecture search, and self-evolving agents?

This is a scientific instrument first and an AI system second. It does not build AGI, it does
not let generated code touch the host, and it never declares the AGM successful. It produces
raw, inspectable measurements.

## Quick start

```bash
python3 scripts/validate_host.py          # Phase 1: host check
pip install -r requirements.txt           # if anything is missing
cp .env.example .env                      # never commit .env
python3 -m pytest                         # unit + integration tests (Docker tests skip if unavailable)
python3 -m experiments.run experiments/manifests/example.yaml
python3 -m experiments.run experiments/manifests/cross_domain_transfer_001.yaml
python3 -m experiments.report --suite cross_domain_001
uvicorn core.api:app --port 8000          # read-only inspection API
```

Results land in `results/<experiment_id>/` (manifest, provenance, telemetry, report) and in the
SQLite database at `results/agm_lab.sqlite` (override with `AGM_DB_PATH`).

`AGM_EXECUTOR=process` (or `--executor process`) runs the same runner as a local subprocess
without container isolation. It is for tests and Docker-less hosts only; every experiment records
which executor produced it.

## Layout

| directory | contents |
|---|---|
| `core/` | entities (`models.py`), ids, capability registry, SQLite layer, FastAPI inspection API |
| `architecture/` | versioned Architecture IR: schema, validation, serialization, hashing, comparison, lineage |
| `compiler/` | IR → sandbox execution spec (pure data, plus static cost/memory/latency estimates) |
| `runtime/` | sandbox executors (Docker, process) and adaptation economics |
| `sandbox/` | the generic runner that interprets compiled specs, and its Dockerfile |
| `environments/` | EnvironmentProfile + dynamic events, synthetic domains, objective scoring |
| `baselines/` | B0 fixed, B1 adaptive, B2 search, B3 self-evolving, B4 bounded AGM prototype |
| `memory/` | structural memory: architectural patterns indexed by environment/task similarity |
| `telemetry/` | JSONL + SQLite telemetry; the only thing agents can observe |
| `experiments/` | manifests, runner, replay, report generator |
| `configs/` | capability registry, adaptive preset library, architecture search space |
| `datasets/`, `results/` | generated data and run outputs (git-ignored) |
| `docs/` | design notes per phase |
| `tests/` | pytest suite |

## What v0.1 does (definition of done, Section 19)

1. Tasks are experiment manifests (`experiments/manifests/*.yaml`).
2. Environments impose CPU, memory, latency, network, capability, deadline and cost constraints.
3. Architecture IR is generated by agents and validated against schema, registry and environment.
4. Validated IR compiles to a sandbox spec executed in a locked-down Docker container.
5. Runtime, CPU time, memory, timeouts and resource violations are measured per execution.
6. Everything is stored in SQLite (`experiments`, `executions`, `evaluations`, `metrics`,
   `environment_events`, `adaptation_decisions`, `architectural_patterns`, `telemetry`, `architectures`).
7. Fixed, adaptive, search, self-evolving and bounded-AGM agents run on identical data, limits and scoring.
8. Provenance (git commit, manifest hash, seed, image id, registry, IR, environment) is recorded and
   `--replay <id>` re-runs an experiment and reports per-step determinism.
9. Environment events fire mid-experiment and every transition is recorded.
10. `report.md`/`report.json` per experiment and a suite report with bootstrap CIs, Pareto fronts,
    resource-normalized comparisons, adaptation overhead, transfer deltas and failed runs.

Not in v0.1 by design: self-modification of code, open-ended architecture invention, LLM-driven IR
proposal (the interface exists: an LLM may only *propose* IR, which goes through the same validation
and compiler), and any distributed infrastructure.

## Honest caveats

* The "models" in the registry (`small_reasoner`, `large_reasoner`, ...) are simulated compute
  profiles executed inside the sandbox, with declared cost/latency/token accounting. No LLM is called.
* The AGM prototype's "synthesis" is heuristic template generation from registry primitives plus
  structural-memory retrieval. Its novelty metric is measured relative to the architectures the
  agent had before the experiment, so read `novelty_mean` with that in mind.
* Wall-clock-dependent quantities (latency violations, deadlines) are inherently non-deterministic;
  predictions and architecture choices are deterministic given the seed and are what replay checks.

See `docs/` for the design of each phase.
